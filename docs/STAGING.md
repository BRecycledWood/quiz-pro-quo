# Permanent Render staging runbook

This runbook and `render.staging.yaml` define one persistent Builder Studio staging environment for PR #1. They do not create, modify, or reference the production Render service, `tryqpq.com`, production data, or production credentials. **Do not use the root `render.yaml` to provision staging.**

## Resources and cost

The Blueprint creates exactly one public Render web service (`quiz-pro-quo-builder-staging`) and one private Render Postgres database (`quiz-pro-quo-builder-staging-db`) in Virginia. The database is separate from production, uses a private internal connection, and has a 1 GB disk with storage autoscaling disabled.

As of 2026-10-29, the smallest always-on web plan is listed at **$7/month** and the smallest paid Postgres plan at **$6/month**, for about **$13/month** on Render's $0 Hobby workspace, before usage overages. The Blueprint uses those plans because Render Free web services sleep after inactivity and Free Postgres expires after 30 days. Pricing details: [Render pricing](https://render.com/pricing) and [Free plan limits](https://render.com/docs/free).

The Hobby workspace currently includes 5 GB monthly outbound bandwidth and 500 build-pipeline minutes; overages are billed. Postgres has 1 GB storage configured; extra storage is currently $0.30/GB/month. Review Render's final quote and any workspace usage before applying. **No billable service or database has been created by this repository change.**

## Provisioning

1. Open the [Render Dashboard](https://dashboard.render.com/), choose **New → Blueprint**, and connect `BRecycledWood/quiz-pro-quo`.
2. Select branch `arena/686d76f2-quiz-pro-quo` and set **Blueprint Path** to `render.staging.yaml` (not `render.yaml`).
3. Review Render's resource diff and price. It must contain only the staging web service and staging database above, on the listed paid plans. Apply only after authorizing the approximately $13/month recurring cost.

No Stripe, SMTP, database, or admin secret needs to be supplied manually. Render generates `ADMIN_KEY` (256-bit random value), creates the separate Postgres credentials, and injects the internal database URL. The stable URL is the service's Render `onrender.com` address; `PUBLIC_APP_URL` follows Render's `RENDER_EXTERNAL_URL`. The exact URL is assigned only after provisioning.

When the service is healthy, open `<render-service-url>/admin/studio`. Copy `ADMIN_KEY` from the service's Render **Environment** page into Builder Studio. Do not paste it into chat, commit it, or put it in a URL. Admin API routes require this key. The service URL itself is public, so use dummy assessment/respondent data and share it only with intended reviewers.

## Environment safety

- `DATABASE_URL` references only the new staging Postgres instance; `ipAllowList: []` blocks public database connections.
- `PUBLIC_APP_URL` is Render-generated, not the production domain.
- `ADMIN_KEY` is generated by Render and never stored in Git.
- `DISABLE_EXTERNAL_SIDE_EFFECTS=true` is enforced server-side. It blocks Stripe client creation and SMTP transport even if credentials are accidentally added later. Stripe and SMTP variables are also blank; no payment webhook is configured.
- `SEED_DEMO_DATA=false` prevents synthetic submissions. The application seeds only its starter assessment catalog in the new database.
- `STAGING_ENV=true` adds `X-Robots-Tag: noindex, nofollow, noarchive` and a disallow-all `robots.txt`.
- The Builder Studio and API are same-origin. No permissive CORS policy or cookie session is used; admin requests carry the generated key. Production HTTPS/HSTS and the existing security headers remain enabled.

## Deploy and migration behavior

The service is pinned to `arena/686d76f2-quiz-pro-quo` and uses `autoDeployTrigger: checksPass`. Render deploys later branch commits only after GitHub checks pass. The build runs `npm ci --include=dev && npm run build`; Render's paid-plan pre-deploy command runs `npm run db:push` before starting the new release. The migration runner uses the same transactional, advisory-lock-protected schema migration path as application startup.

`/healthz` checks database connectivity and returns the storage kind plus boolean integration-status flags; it never returns credentials. Render requires a 2xx/3xx response within 5 seconds. A new instance must pass before receiving traffic; a failed new deploy is canceled after 15 minutes while the prior release continues serving. For a running instance, Render stops routing after 15 seconds of consecutive health-check failures and restarts it after 60 seconds. The web process drains HTTP requests and closes its database pool after SIGTERM, with a 25-second internal deadline and Render's 30-second maximum. On updates, a failed build or pre-deploy migration leaves the prior release and staging database in place. The database is an independent managed resource and is not deleted by app redeploys.

## Diagnosing deployment issues

- **No new deploy:** confirm the service is linked to the named development branch and its GitHub Actions checks completed successfully. This repo runs CI on pushes to that branch.
- **Build failure:** open the Render service's **Events/Deploys** details and inspect the build log; verify the Node runtime and locked `npm ci` install.
- **Migration failure:** inspect the pre-deploy log. Render will not activate that release. Do not manually point staging at production to work around a failure.
- **Health check failure / 503:** check that the database is Available, the service and database are both in Virginia, and the private `DATABASE_URL` reference resolves. Expected `/healthz` fields are `ok: true`, `storage: "postgres"`, `publicAppUrlConfigured: true`, `stripeConfigured: false`, and `emailConfigured: false`.
- **Builder Studio login failure:** retrieve the staging service's generated `ADMIN_KEY` from Render Environment and enter it at `/admin/studio`; never use a production key.

## Rollback, backups, and recovery

Use the service's **Deploys** page to roll back to the previous successful application release. An application rollback does **not** reverse database migrations. Current schema upgrades are transactional and additive; if a migration fails, the pre-deploy command aborts before the new release is activated. Do not manually drop or rewrite staging tables as a rollback strategy.

Paid Render Postgres on the Hobby workspace provides continuous point-in-time recovery for the past **3 days**. Render also supports on-demand logical exports, retained for **7 days**. Before major staging work, create an export from the database's **Recovery** page if a longer restore point is useful. See [Render Postgres backups and recovery](https://render.com/docs/postgresql-backups).

For recovery, use the database's **Recovery → Restore Database** flow to create a separate recovery instance at the desired time. This adds another paid database while both instances exist; review and approve the temporary additional cost first. Verify the recovery instance before switching the service. Update the service's `DATABASE_URL` to the recovered database's **internal** connection string, then reconcile `render.staging.yaml` so its `fromDatabase.name` points to the recovered resource before the next Blueprint sync. Review Render's proposed Blueprint changes and do not apply if they would create an unintended database. Keep the original database until the recovered service passes `/healthz` and Builder Studio checks; delete neither database until the recovery is confirmed.
